# Sitzungszusammenfassung 2026-08-29

> Entwicklungssitzung EMS-Proxy auf Teltonika RUTX11.
> Ergebnis: PR #1 in main gemergt, Snapshot-Branch `snapshot/v0.9-simulation`.
> Detail-Ledger: siehe docs/Learnings.md und docs/PowerShell-Log.md.

## Ausgangslage

- Alt-Code war zu ~50 % vorbereitet: modbus_proxy.lua / powersplit.lua Skeletons,
  mehrere CGIs leer (0 Bytes), HTML-Seiten mit JS-Fehlern, Watchdog ohne Failsafe.
- Ziel: Modbus-TCP-Proxy zwischen Tesvolt EMS (Master, Port 1502) und zwei
  Batteriespeichern (Tesvolt + BLUESUN 120KW/261KWH via UDAN-EMS) mit
  gewichtetem Leistungssplit.

## Chronologie der Sitzung (Probleme -> Diagnosen -> Fixes)

1. **Erstes Deployment auf den Router**
   - BusyBox-wget kann keine HTTP-Header -> curl-first in github_update.sh
   - / ist squashfs READ-ONLY -> Deploy-Ziele /usr/local/bin, /usr/local/www, /etc
   - Eigene uhttpd-Instanz 'emsproxy' Port 8080 (Port 80 gehoert der RUTOS-WebUI)

2. **Setup-UI speicherte nicht**
   - Diagnose via debug.cgi: uhttpd fuehrt CGIs als User 'uhttpd' (uid 575) aus,
     kein Schreibrecht auf /etc
   - Fix: Update-Skript legt alle /etc/tesvolt_*-Dateien an + chown uhttpd + chmod 664

3. **Proxy-Restart-Schleife (alle ~8 s)**
   - Ursache 1: Watchdog nutzte modbus_cli, das auf RUTOS nicht existiert
     -> eigener Client mb_cli.lua (luasocket); Watchdog-Logik: EXC = Proxy lebt
   - Ursache 2: Proxy (single-threaded) blockiert beim Connect auf nicht
     existierende Test-IPs laenger als der Check-Timeout
     -> Simulationsmodus (/etc/tesvolt_sim=1): Fantasiewerte ohne Upstream-Connect

4. **Alte Sim-Werte trotz Update (SOC_B=341)**
   - Ursache: Lua laedt Code NUR beim Prozessstart - laufender Proxy behielt
     alten Code im Speicher
   - Fix (Commit 88c35c3): github_update.sh killt nach dem Update den laufenden
     Proxy, Watchdog startet binnen ~5 s mit frischem Code (Regel 11)

5. **UI-Plausibilitaetspruefung** (Commit 042e360)
   - Transport-OK heisst nicht fachlich plausibel: SOC 341 % wurde gruen angezeigt
   - PLAUSIBLE-Map in status.html (SOC 0-100 %, Power +-150 kW); Verletzung ->
     gelb "UNPLAUSIBEL", Wert fliesst nicht in Power-Panel/SOC-Balken/Historie

6. **Status-UI ausgebaut**
   - Drei-Spalten-Layout: Register-Tabelle | Power-Panel (Gesamt + Tesvolt/BLUESUN
     einzeln, Richtung LADEN/ENTLADEN/STANDBY) | SOC-Balken
   - Verlauf 24 h im 5-min-Raster, Historie im Browser (localStorage, 288 Buckets,
     Pruning); zuerst als Farb-Heatmap (Commit 0045d5a), auf User-Feedback hin
     ersetzt durch Flaechendiagramme (Commit 4c873d4): 80 px hoch, Min/Max-Achse,
     gestrichelte Nulllinie bei Vorzeichen-Signalen, Datenluecken bleiben Luecken

7. **Grid-Limit-Feature (max. Netzanschlussleistung)** (Commits 771274f, 40e388a, 1b1a4c1, b9ef61a)
   - Entscheidungen (User): wirksames Limit = min(Setup-kW, EMS-Register 40003/40004);
     EMS-Quelle per Checkbox, default AUS (Einheit/Skalierung UNVERIFIZIERT);
     kein Limit gesetzt -> nur oranger Warnhinweis; Clamping NUR im Split-Modus
     (im Passthrough kein Eingriff in die Tesvolt-Steuerung)
   - powersplit.lua: Clamp VOR dem Split + proportionale Sicherung NACH der
     Rest-Umverteilung (sonst koennte die Summe das Limit wieder ueberschreiten)
   - Konfigdateien /etc/tesvolt_grid_max_chg/_dis/_use_ems (Update-Skript legt an
     + chown uhttpd); Setup-Sektion "Netzanschluss (Grid-Limit)"; Anzeige in
     status.html als eigene Tabelle "Netzanschluss-Grenzwerte" neben den
     PowerSplit-Parametern

8. **Herstelleranfrage UDAN-EMS formuliert** (englisch, per Mail versandt)
   - Kernfrage: Schreibpfad Pfad A (0x1500=2 manuell + 0x1501 Kategorie +
     0x1502 ExpectedPower, 0,1 kW) vs. Pfad B (0x1530/0x1531 PCS-direkt,
     Offset 3000, 1 kW)? Bisheriges Mapping SetPower_B=0x1144 ist FALSCH
     (0x114x ist read-only). Antwort steht aus.
